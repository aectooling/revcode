# Skills library and authoring

The host stores preferences and the default `skills` folder in its shared user data directory. Browsing is available without a model provider or Revit connection. Enabled skills are available for discovery; selected skills are explicitly read before work; read evidence records the exact revision and range and is not proof of compliance. Disabling a skill cannot remove instructions already in conversation history.

Loose Markdown files are skills. A `SKILL.md` directory owns its Markdown and C# supporting files, stopping at nested skill roots. Loose C# files are ignored, and examples never execute automatically. IDs combine source, canonical root and normalized relative path; Windows case aliases share identity. Moves/renames can create new IDs.

Discovery allows 500 supported files per library, 256 KiB per file, and 16 directory levels. Oversized, unreadable and escaping linked files are disclosed. The SDK-generated metadata catalog is limited to 24 KiB, each ranged read to 16 KiB, and cumulative skill context to 128 KiB including the catalog and read framing. Explicit selections reserve catalog space before remaining entries in stable ID order. Oversized selections are rejected before acceptance. Bounded search covers omitted enabled entries. Reads come from copied run-snapshot bytes, never live filesystem fallback.

Authoring checks the projected supported-file count for the entire user library before writing, including loose C# and oversized files counted by discovery. Updates at capacity may preserve or reduce the file count; restores release capacity for removed files. Hidden paths and paths beyond the discovery depth cannot be authored. Snapshot and authoring reads end on UTF-8 character boundaries; continue with the returned `nextOffset`. Offsets inside a character and limits too small to read the next character are rejected.

Skill authoring mode registers only skills/history tools. It cannot execute native C#, capture views, or control the desktop. It may read a disabled user skill for editing, labeled as authoring evidence rather than activation. New and revised content applies to subsequent runs. Skills should retain source instance/run references, describe observed success honestly, parameterize incidental IDs and avoid persisting secrets.

Preference and authoring updates use the same cross-process lock, with expected preference revision, root and content revision. Writes accept only normalized `.md` and `.cs` paths under one user skill; traversal, filesystem links, nested skill overlap and Windows destination collisions are rejected. Bundled skills are immutable. External editors do not honor the lock: observed changes produce conflicts, but check-and-replace cannot eliminate every external-write race.

Each skill retains up to 10 revision records with an 8 MiB serialized budget, including complete before/after file content and saved changes. The immediately preceding complete revision must fit or the save fails before any files change. Older revisions expire explicitly. Restore checks the current root/revision, saves a new revision and restores the complete supported file set, including removing files introduced by the reverted change. Enabled state is preserved.

Multi-file saves are recoverable, not atomic. A `.pending.json` transaction in shared `skill-revisions` stores complete before/after bytes before replacement begins. On initialization, the host rolls an interrupted save back when every destination still matches its recorded before or after state. If an external edit prevents safe rollback, the browser reports the recovery record and further authoring is blocked; retain that file and reconcile the external content before calling `recoverPending()` or restarting. Recovery never guesses which external content to overwrite. Successful saves publish revision history and remove the pending record.

Transactions are written and flushed to a temporary file, then published by rename before any skill file changes. An interrupted unpublished temporary file is ignored during recovery. Malformed or unrecoverable published records are retained and reported, blocking authoring while allowing the host to start and the library to be browsed.

The Pi integration uses installed SDK resource-loader overrides and tool lifecycle events. Starts are persisted before execution, native descendants run in their tool-call context, and lifecycle writes are drained before the prompt returns. General shell/edit/write tools remain disabled.

Agent authoring is pinned to the library root and preference revision accepted at run start. A settings change during a run causes an authoring conflict instead of redirecting a later write. Structured source instance/run references come from the host, replace model-supplied provenance, and are retained through later updates. A requested destination skill is enforced. Disabled bundled skills may be read for copying into a new user skill; they remain immutable and copy-only.
